# 后端接口对接请求（前端 → 后端）

> 目的：让前端「添加视频（仅视频）→ 点击开始 → 动态演示手语识别全过程」能**真正调用后端**，
> 而不是只跑前端 mock。本文档是给后端同学的**改动请求**，前端代码改动暂缓，等后端接口就绪。
>
> 配套约束：
> - 前端接口规范：`docs/前端接口对接规范.md`（禁止组件内裸写 axios、URL 集中 api/、统一响应 `{code,msg,data}`、loading/取消/异常分层等）
> - 层间契约（唯一事实源）：`tests/contract.py`（`GLOSS_SCHEMA` / `AGENT_SCHEMA` / `(T,27,3)` 骨架）
>
> 现状说明（后端同学请注意）：目前 `app/app.py` 是 **Gradio** 界面，没有 REST `/api` 服务；
> 真实链路逻辑在 `app/pipeline_demo.run_demo_from_source(video)`、`app.e2e_pipeline.run_e2e(seq, predictor)`。
> 本次需要新增一个 **HTTP 服务**，把这两段逻辑包成契约接口，供前端调用。

---

## 一、统一约定（前后端共用）

- **Base URL**：`/api`（开发由 Vite / `serve.py` 反代；生产用 Nginx 反代）。**禁止前端写死 IP/域名**。
- **统一响应包**：
  ```json
  { "code": 0, "msg": "success", "data": { } }
  ```
  - `code`：业务码，`0` 成功；非 0 见下表。HTTP 状态码仍用 200/400/401/403/500。
  - `msg`：错误/提示文案（前端 toast 用，**文案由后端给，前端不自己编造**）。
  - `data`：业务数据（下文各接口的返回都放在 `data` 里）。
- **鉴权**：请求头 `Authorization: Bearer <token>`；`401` 由前端拦截器统一跳登录/清 token，
  后端只需在缺/错 token 时返回 `401` + `{code:401, msg:"未登录"}`。本系统无登录也可先放行（mock 阶段），但接口要预留。
- **视频上传**：`multipart/form-data`，字段名 `video`；**仅接受视频**，后端必须二次校验真实类型（前端只做提示，不可信）。
  - 允许的 MIME / 后缀：`video/mp4`、`video/avi`、`video/quicktime`(mov)、`video/webm`；大小上限建议 `50MB`。
  - 非法文件返回 `400` + `{code:400, msg:"仅支持 mp4/avi/mov/webm 视频"}`，**不要静默当图片处理**。

## 二、需要新增的接口

### 1. 识别层：`POST /api/recognition`
- **入参**（multipart）：`video` 文件。
- **出参** `data`（契约 `GLOSS_SCHEMA`，见 `tests/contract.py`）：
  ```json
  {
    "gloss_sequence": ["我","冷","窗","关"],
    "confidence":     [0.92, 0.58, 0.91, 0.85],
    "timestamps":     [[0.0,0.4],[0.5,0.9],[1.0,1.4],[1.5,1.9]],
    "margin_top1_top2": [0.3,0.1,0.4,0.2],
    "low_confidence":   [false, true, false, false]
  }
  ```
- 内部调用：`app.pipeline_demo.run_demo_from_source(video)` 的 gloss 部分（或 `e2e_pipeline` 的 `merge_segment_glosses`）。
- **同步返回即可**（识别通常秒~十秒级）；前端会带 loading + 防重复提交。

### 2. 端到端：`POST /api/pipeline`
- **入参**（multipart）：`video` 文件。
- **出参** `data`（`PipelineResult`）：
  ```json
  {
    "recognition": { /* GLOSS_SCHEMA */ },
    "agent": {
      "natural_language": "我觉得冷，能关一下窗户吗？",
      "intent": "command",
      "task": "close_window",
      "clarification": false,
      "low_confidence_words": ["冷"]
    }
  }
  ```
- 内部调用：`app.pipeline_demo.run_demo_from_source(video)` 全链路（契约闸门已内置）。
- 该接口给「一次性拿全量结果」的场景用。**动态演示建议走下面的流式接口。**

### 3. 动态演示（关键）：`POST /api/pipeline/stream` —— **分阶段流式返回**
前端需要「识别过程中动态演示过程」：视频读入 → 骨架 → 切分 → 识别 → 智能体三步 → 应用执行，
每一阶段前端要**边算边渲染**。请用 **Server-Sent Events (SSE)** 实现（`text/event-stream`，`event`/`data` 行）。

- **入参**（multipart）：`video` 文件；可选 `jobId`（断点/幂等用，首调用可不带）。
- **流协议**：每个事件是一行 JSON（`data: {json}\n\n`）。建议事件类型 `type` 字段如下：

  | type | 含义 | data 关键字段（契约对齐） |
  |---|---|---|
  | `stage` | 阶段开始/切换 | `stage`: `perception`/`segmentation`/`recognition`/`agent_step1`/`agent_step2`/`agent_step3`/`application`；`label` 中文描述 |
  | `perception_done` | 感知完成，骨架就绪 | `shape`: `"[T,27,3]"`，`numFrames`, `fps`, `durationSec`；`skeletonUrl`(可选，见下) |
  | `segmentation_done` | 切分完成 | `segments`: `[{startTime,endTime}]`，`numSegments`, `numWindows` |
  | `recognition_window` | 每个窗口识别产出（可多次） | `window`: `{startTime,endTime,gloss,confidence}`（用于实时滚动展示，最后再聚合） |
  | `recognition_done` | 识别聚合完成 | `recognition`: `GLOSS_SCHEMA` 全量 |
  | `agent_step` | 智能体每一步（可多次） | `step`: 1/2/3，`promptSystem`,`promptUser`,`output` |
  | `agent_done` | 智能体完成 | `agent`: `AGENT_SCHEMA` 全量 |
  | `application` | 应用层执行 | `apiPath`, `taskName`, `task`, `controllerStatus`, `changes`:`[{label,from,to}]` |
  | `done` | 全部完成 | 整体 `PipelineResult`（同 `/api/pipeline` 出参） |
  | `error` | 出错 | `code`,`msg` |

- **骨架数据怎么给前端播放**：`perception_done` 阶段可二选一（后端定）：
  - (a) 返回 `skeletonUrl`，前端再 `GET /api/skeleton/:jobId` 拉 `(T,27,3)`（建议压缩成行优先 JSON 或 `.npz`）；
  - (b) 直接把 `(T,27,3)` 放进 `perception_done.data.skeleton`（帧数少时可直接传，前端 `SkeletonCanvas` 已支持 `(T,27,3)`）。
  - 前端播放器 `SkeletonCanvas` 已按 `perception/skeleton.py` 的 `HAND_EDGES`/`POSE_EDGES` 渲染 27 点，所以后端给的原始 `(T,27,3)` 即可直接喂。

- **取消**：前端用 `AbortController` 中断 fetch；后端收到断开即停止计算（或提供 `POST /api/pipeline/:jobId/cancel`）。

> 说明：SSE 用 `fetch` + `ReadableStream` 读（axios 不支持 SSE，前端会单独封装一个 `streamPipeline`），
> 这与「统一用 request.ts」不冲突——流式是特例，单独封在 `api/pipeline.ts` 里。

## 三、与现有后端的映射（给后端同学的接线提示）

| 接口 | 建议调用 |
|---|---|
| `/api/recognition` 出参 | `app.pipeline_demo.run_demo_from_source(video)["gloss_json"]`（经 `validate_gloss_output`） |
| `/api/pipeline` 与 `/stream` | `run_demo_from_source` 全链；或 `app.e2e_pipeline.run_e2e(seq, predictor)`（需 `Predictor` + `AgentPipeline`）。`run_e2e` 已分 4 步，天然适合拆成 SSE 事件 |
| 骨架 `(T,27,3)` | `perception.extract.extract_video(video, cfg)["skeleton"]`（需 mediapipe+opencv；缺依赖时返回 `error` 事件，前端降级到 mock 演示） |
| 契约校验 | 全程 `from tests.contract import validate_*`，不合法即抛错，前端收到 `error` 事件 |

**降级要求**：感知/识别依赖（torch / mediapipe / opencv）若未安装，接口**不要 500 崩**，
返回明确 `error` 事件 `{code:503, msg:"后端推理依赖未就绪（缺 torch/mediapipe）"}`，
前端据此自动回退到 mock 演示（spec 允许「数据无关先行」）。

## 四、需要后端确认 / 拍板的点

1. **框架**：建议 `FastAPI`（原生 `StreamingResponse` 最适合 SSE；依赖 `pip install fastapi uvicorn`）。若后端坚持 Flask/现有 Gradio 挂 HTTP，请说明怎么发 SSE。
2. **骨架传输**：`(T,27,3)` 走 `skeletonUrl` 二次拉取，还是直接内联在 SSE 事件里？（影响前端播放器接入方式）
3. **鉴权**：当前是否要求登录？不要求的话接口先放行，但响应头要预留 `401` 路径。
4. **服务启动方式**：新增的 HTTP 服务怎么和现有 Gradio 共存？建议 `app/server.py` 独立端口（如 8000），`serve.py --backend` 反代 `/api` 到它（而不是 Gradio）。
